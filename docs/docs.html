Why group leaks usually go unsolved

The copies are identical

Every recipient decrypts the same bytes, so a leaked file carries no trace of which decryption produced it.

Access logs can be rewritten

Server logs sit under a privileged administrator who can quietly alter or erase the record.

Static watermarks repeat the problem

A mark added before distribution is the same for everyone, so it points at the whole group, not a person.

Four layers, built at the moment of decryption

Scroll to assemble the stack. The highlighted layer is the one described.

Layer 0

Encryption foundation

The document is encrypted once with AES-256-GCM. Its key is wrapped separately for each recipient with ML-KEM-768, so no classical RSA or ECC is used anywhere in the key exchange.

Layer 1

Forensic fingerprint

When a recipient decrypts, a watermark tied to that session is embedded invisibly. Reed-Solomon error correction lets it survive partial copies, screenshots and JPEG re-compression.

Layer 2

Non-repudiation

The recipient signs the decryption record with their own ML-DSA-65 private key. Only they could have produced that signature, so they can't later deny opening the file.

Layer 3

Tamper-evident ledger

Two of three independent validator organizations endorse the record before it joins a hash-chained, append-only ledger. Editing any entry breaks both the chain and the signatures.

From leaked file to named recipient

  1. 1

    Distribute

    The sender uploads a file and picks recipients. It's encrypted once and wrapped for each of them.

  2. 2

    Decrypt

    A recipient opens it. The fingerprint, signature and ledger entry are created in the same action.

  3. 3

    Leak

    A copy turns up outside the group, whole or as a pasted fragment.

  4. 4

    Trace

    The fingerprint is extracted, matched on the ledger and verified against the recipient's signature.
